# 🦆 Teal Deal — one duck shop, every tier on DuckDB

A toy e-commerce platform where **DuckDB is the database for everything**: the
transaction that sells a duck, the clickstream that recorded the visit, the
analytics that chart it, and the catalog search running in the customer's
browser. One engine, wired together with `ATTACH` so a single query can span
tiers, plus a DuckLake catalog (Parquet + real snapshots) as the append-only lake.

The point is partly a joke on DuckDB itself: it's an embedded *OLAP* engine, so
the transactional tier is the part that *shouldn't* work — which makes it the
most interesting corner to build, and the one seam left deliberately visible.

```
oltp.duckdb        transactions: users, products, inventory, orders  (single writer)
tracker.js         browser tracker: fires pageview/add_to_cart events
make_sprites.py    generates public/ducks.svg, one drake sprite per species
collector.py       single-writer collector: storefront + events + real checkout + live stats
teal_deal_catalog.ducklake + lakehouse_data/   clickstream lake (DuckLake catalog, append-only truth)
06_ducklake.sql    explores the live catalog                         (snapshots + time travel)
07_stress.py       concurrent-writer stress test over quack          (multiple writers, live)
marts.duckdb       downstream analytics: sessions, funnel, retention  (attaches oltp + the lake)
public/index.html  DuckDB-WASM catalog search (BM25 fts) + real cart/checkout + live recs
public/dashboard.html   funnel/revenue/retention, live from oltp.duckdb + the lake, no rebuild
```

## Run it

```bash
./run.sh                      # builds everything, then serves it — no extra steps
```

Seeds OLTP, lands the clickstream in a DuckLake catalog, exports the browser
catalog, builds the marts, runs the extensions showcase and the snapshot/
time-travel exploration (both best-effort — see below), then starts
`collector.py` as its last act:

- **http://localhost:8787/** — the storefront, DuckDB-WASM catalog search + real checkout
- **http://localhost:8787/dashboard.html** — Duck HQ, the live dashboard

Both pages have a **🩻 X-ray** button that shows which part of DuckDB powers what: a
legend under the header, linked labels beside each feature (DuckDB-Wasm, Parquet,
`fts`, `vss`, DuckPGQ, triggers, DuckLake, Quack …), a tag on each row of the
live-query drawer — and the ducks turn into x-rays, skeletons and all. The labels
report what actually loaded (if `fts` can't, search says it fell back to `ILIKE`).
It's off by default, remembered per browser, and `?xray` in the URL turns it on.
The code is `public/xray.js` + `public/xray.css`; every outbound link is in one
table at the top of `xray.js`, and `make check-links` requests each of them (run it
before deploying — docs URLs move). The skeleton is generated by `make_sprites.py`.

Ctrl-C stops it (flushes cleanly on exit). Re-running `./run.sh` is always
safe — it stops whatever server a previous run left up before rebuilding, so
you never get a "port already in use" error.

A `Makefile` wraps the common tasks (`make help` lists them):

```bash
make run        # same as ./run.sh
make build      # rebuild the data, don't serve        (./run.sh --build-only)
make serve      # serve what's already built
make public     # serve behind a local TLS proxy with the lake's quack endpoint read-only
make up         # same, but app + proxy both in containers (docker compose)
make down       # remove the containers
make browser    # open the public-mode dashboard in a throwaway browser profile
make check      # confirm the public quack endpoint refuses writes
make stop       # stop the collector, containers and throwaway browser
```

`make public` and `make up` are the local rehearsal of a public deployment.
Caddy (see `deploy/Caddyfile.local`) terminates TLS for `teal-deal.test`, and
`TEAL_DEAL_PUBLIC=1` makes the collector refuse every quack write and file read,
so the page's quack token being public is harmless. `make public` runs the
collector natively next to a Caddy container (Linux only: Docker host networking);
`make up` runs both in containers and works anywhere Docker does.

**Abuse limits** (always on, `collector.py`): `/collect` and `/order` — the two
endpoints that write — have per-IP and global token-bucket rate limits (429 with
`Retry-After`), a 16 KB body cap, and strict validation: only the tracker's event
types, integer ids, at most 20 events per request, orders of 1–10 of a product
(a negative quantity would otherwise add stock). The read endpoints are limited
too. Behind the proxy the client IP comes from a header the proxy sets
(`TEAL_DEAL_CLIENT_IP_HEADER`: `X-Forwarded-For` for Caddy, which overwrites it;
`CF-Connecting-IP` behind Cloudflare, where `X-Forwarded-For` can be spoofed), so
the limits can't be dodged by lying about your address. Limits live in the `LIMITS` table at the top
of the abuse section; `make test` covers them. Not covered: queries sent straight
to the read-only quack endpoint (only `quack_server_max_connections` caps those),
and a distributed flood can still use up the global order limit and lock out
real shoppers — fine for a demo.

The `Dockerfile` bakes everything into the image: the pinned 2.0.0 CLI, the Python
deps, every DuckDB extension, and the seeded data (`run.sh --build-only`), so a
container needs no network at runtime and always starts from the seeded state.
`make up RESET=1` recreates the app container to reset the demo. The site and
quack share one origin — quack's client always POSTs `/quack`, so the proxy sends
that path to the lake and everything else to the collector — on one published
port (8443). The proxy shares the `app` container's network namespace, which is
how it reaches quack on loopback.

Needs the `duckdb` CLI on your PATH (or `DUCKDB=/path/to/duckdb ./run.sh`) and
[`uv`](https://docs.astral.sh/uv/) — `run.sh` calls `uv sync` itself, which
installs the pinned `duckdb==2.0.0` into `.venv` for `collector.py`. The CLI
must be 2.0.x too (`curl https://install.duckdb.org | bash`); 2.0 database
files can't be read by older versions. The community `duckpgq` extension (hybrid recommendations, see below) needs
`SET active_grammar_extensions = ['duckpgq']` after `LOAD` on 2.0 — the scripts
do this; if the extension is unavailable that one feature degrades gracefully
rather than breaking the app. Also needs
network: the DuckLake catalog (`03_lake.sql`) requires it on first run to
install the `ducklake` extension (cached after that) — that's a core
dependency, not an optional tier. `05_extras.sql` (fts/vss/spatial/DuckPGQ),
`06_ducklake.sql` (snapshot exploration), and `collector.py`'s own DuckPGQ
setup all run **best-effort**: if their extensions can't be reached (e.g. the
community `duckpgq` host is down, or its build hasn't caught up to your
DuckDB version), each logs it and keeps going rather than failing the whole
build/app over an optional tier.

Want to re-run one piece by hand — e.g. after editing `05_extras.sql` —
without rebuilding everything? Stop the collector first (only one process can
have the DuckLake catalog attached at a time), then:

```bash
duckdb oltp.duckdb -f 05_extras.sql             # fts / vss / spatial / DuckPGQ
duckdb -f 06_ducklake.sql                       # explore the live catalog: snapshots + time travel
duckdb marts.duckdb -f 04_marts.sql             # rebuild marts after live collector.py traffic
```

## Deploying: a Hetzner node behind a Cloudflare Tunnel

`compose.prod.yaml` runs the app plus `cloudflared`. The node publishes **no ports**:
`cloudflared` dials out to Cloudflare, which terminates TLS and sends visitors back
through the tunnel, so the Hetzner firewall needs only SSH. (That is also what makes
the rate limits' use of `CF-Connecting-IP` trustworthy — there is no other way to
reach the collector.) The Dockerfile builds for x86 and ARM (CX/CPX or CAX nodes).

1. **Tunnel.** Cloudflare Zero Trust → Networks → Tunnels → create a `cloudflared`
   tunnel and copy its token. Add two *Public Hostnames* for `tealdeal.dorzey.net`, in
   this order (`deploy/cloudflared.example.yml` has the same rules written out):
   1. path `^/quack` → HTTP `127.0.0.1:8789` (the lake's read-only quack endpoint)
   2. no path → HTTP `127.0.0.1:8787` (storefront, dashboard, `/collect`, `/order`)

   One hostname, split by path, because quack's client always POSTs `/quack`; the
   site and the lake share an origin, so there is no second hostname and no CORS.
2. **Node.** Docker with the compose plugin; `git clone` this repo.
3. **Configure and start.**
   ```bash
   cp .env.example .env        # set TUNNEL_TOKEN (and TEAL_DEAL_QUACK_URL if not tealdeal.dorzey.net)
   docker compose -f compose.prod.yaml up -d --build
   ```
4. **Check.** `https://tealdeal.dorzey.net/` shows the shop, `/dashboard.html` fills in
   (funnel, retention and daily activity come from the browser over `/quack`), and
   `curl https://tealdeal.dorzey.net/config` returns `quack:tealdeal.dorzey.net:443`.
5. **Reset** the demo (fresh seed data, empty lake) by recreating the containers —
   both, because `cloudflared` is attached to the app's network namespace:
   `docker compose -f compose.prod.yaml up -d --force-recreate`. A nightly cron entry
   does this: `0 4 * * * cd /opt/teal-deal && docker compose -f compose.prod.yaml up -d --force-recreate`.

Things to watch on a Cloudflare-fronted site: turn off *Rocket Loader* and *Auto Minify*
(they rewrite scripts), and if the tracker's `POST /collect` or the dashboard's `POST
/quack` are being challenged or blocked, check *Bot Fight Mode* and any WAF rules for
this hostname — browsers can't solve a challenge on a background POST. Both pages
load the DuckDB-Wasm engine from jsDelivr, not through Cloudflare: about 7 MB over
the wire per build on first load (it unpacks to ~45 MB in memory).

## The tiers

**`01_seed.sql` · `02_oltp.sql` — transactional (the "wrong tool" corner).**
Real `PRIMARY KEY` / `REFERENCES` / `CHECK` constraints and a `SEQUENCE`. The
place-order flow is a genuine `BEGIN … COMMIT`: allocate an order, decrement
inventory, write line items, all-or-nothing. `CHECK (stock >= 0)` does the job a
pessimistic row lock would do elsewhere — try to oversell and the whole
transaction rolls back. DuckDB is single-writer, so the honest way to run an
app on it is to funnel every write through **one serializing process** holding
the sole write connection; readers use separate read-only connections.

Two DuckDB 2.0 **triggers** keep the stock honest, in the database rather than in
`collector.py`, so every writer gets them. `trg_stock_audit` logs each inventory
change to `stock_audit`. `trg_restock` is the demo's self-healing: when an order
leaves a product under 5 it is topped back up to 40 (a "supplier delivery") inside
the same transaction, so a public demo can't sell itself empty. Two limits shaped
it: a trigger can't update its own table ("recursive trigger chains are not yet
supported"), so it hangs off `order_items` rather than `inventory`; and triggers
live inside one database, so they can't reset the DuckLake events or the whole
demo — for that, recreate the container (`make up RESET=1`). `02_oltp.sql` shows
the restock happening.

**`03_lake.sql` — web analytics.** A tracker's `pageview` / `add_to_cart` /
`purchase` events land directly in a **DuckLake catalog** (not a bare Parquet
directory), with a semi-structured JSON `props` column so the schema can
evolve without a migration. Every commit is a snapshot, giving versioning,
`AT (VERSION => n)` time travel, and a change feed for free. `03_lake.sql`
synthesizes a month of events in three chronological waves, so there are
three real snapshots to explore right away; the **live path** is `tracker.js`
+ `collector.py`.

**Event tracking (the live path).** `tracker.js` runs in the storefront: it
keeps a durable anonymous `visitor_id` and a 30-minute `session_id`, fires a
pageview on load, and sends an `add_to_cart` event when you click a card —
using `navigator.sendBeacon` so events survive page unloads. `collector.py` is
the receiving end. Like the OLTP tier, it's a single writer — two of them, in
fact: one connection for `oltp.duckdb` (orders, recommendations, the
dashboard's revenue) and a separate one for the DuckLake catalog (event
flushes, the dashboard's funnel/retention). It serves the storefront (so
events post same-origin), batches events, and `INSERT`s each batch straight
into the DuckLake catalog in the *same schema the marts read* — live clicks
flow into the funnel and retention next time you build the marts. A
background thread calls `ducklake_merge_adjacent_files` every 60s, DuckLake's
documented answer to the small-file fragmentation that batched inserts
produce.

The DuckLake connection also calls `quack_serve()` —
[Quack](https://duckdb.org/2026/05/12/quack-remote-protocol.html) is DuckDB's
own HTTP client-server protocol, core since v1.5.3. A second process can
`ATTACH` to it over the network and read/write events *while the collector
keeps running*, instead of needing the file directly:

```bash
duckdb -c "
  INSTALL quack; LOAD quack;
  ATTACH 'quack:localhost:8789' AS remote (TOKEN 'teal-deal-demo-token');
  SELECT event_type, count(*) FROM remote.events GROUP BY event_type;
"
```

`oltp.duckdb` is quack-served too, on port 8790 (same token). Every table
there has a `FOREIGN KEY`, which quack's beta couldn't expose; 2.0 can. Remote
writes still funnel through `collector.py`'s one connection, so the
single-writer limit stands.

`public/dashboard.html` is the more interesting client: its
funnel/retention/daily-activity charts are computed by DuckDB-WASM running
*in the browser*, attached straight to `collector.py`'s live DuckLake
connection over quack — the same thesis as the storefront's in-browser
search, against a live server instead of a static Parquet export. These
three charts are quack-only, with no `/dashboard-data` fallback:
`get_dashboard()` only computes `revenue_by_category`/`totals` (the numbers
that need `oltp.duckdb`; the dashboard doesn't attach to it yet). Until the in-browser
connection finishes instantiating, or if a live query fails, those three
cards show a "waiting for the live Quack connection…" placeholder instead of
stale or re-fetched data. Uses Query Farm's Haybarn build,
`@haybarn/haybarn-wasm@2.0.0-rc12` (from jsDelivr): the first published wasm build
on the DuckDB 2.0 engine whose quack extension can `ATTACH` to a 2.0 server —
`@duckdb/duckdb-wasm` is still 1.5.x and speaks an older quack protocol. Only the
threaded variant works (quack needs real threads), so the collector serves
`dashboard.html` with `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: credentialless`. The storefront uses the same package
at the same pinned version (`test_pages.py` checks they agree) but its non-threaded
build: the shop needs no quack, so no cross-origin isolation. Haybarn ships only
those two builds, with no fallbacks for browsers lacking WebAssembly exception
handling, and its extension files are replaced in place (see the note in
`dashboard.html`) — the two reasons to move both pages to the official
`@duckdb/duckdb-wasm` once it ships a 2.0 build that can attach to a 2.0 quack server.

**Concurrent writers (`07_stress.py`).** N threads, each with its own quack
connection, `INSERT` into the live DuckLake catalog at once — a real exercise
of Quack's "multiple concurrent writers" claim:

```bash
uv run 07_stress.py --workers 8 --duration 10
```

Writes use real event types (weighted like real traffic — mostly pageviews)
and land in the exact same table the dashboard reads, so a run visibly moves
the live sessions/funnel/retention/daily numbers rather than a separate
counter off to the side. Each row is tagged `props: {"stress": true}` so the
dashboard's own "⚡ N writes · N/s" banner can count them separately from
organic traffic. Under enough concurrent write pressure, a transaction can
exhaust its retry budget and fail outright (`Exceeded the maximum retry
count... Conflict on update!`) — DuckLake uses optimistic concurrency, not a
queue, so contention shows up as retried-then-failed writes rather than
serialized waiting.

**`06_ducklake.sql` — time travel over the lake.** Explores what
`03_lake.sql` already landed: `ducklake_snapshots`, `AT (VERSION => n)` /
`AT (TIMESTAMP => …)` time travel, and a change feed via
`ducklake_table_changes`, replaying the funnel as of an earlier snapshot.
Needs the file directly (stop `collector.py` first) — `ducklake_snapshots()`
doesn't work through a quack attachment, though `AT (VERSION => n)` does.

**`04_marts.sql` — downstream analytics (home turf).** `ATTACH`es the OLTP store
read-only and reads the lake in the same queries. Sessionization via window
functions (30-min inactivity gap ⇒ new session), a session-level view→cart→
purchase funnel, retention cohorts (a cross-database join of lake activity to
OLTP signup + country), and a revenue rollup.

**`05_extras.sql` — the fun tier, all just extensions.** BM25 full-text search
(`fts`), HNSW vector similarity over real text embeddings (`vss`), a co-purchase
graph you traverse with a real `MATCH` (DuckPGQ), nearest-warehouse fulfilment
(`spatial`), a live remote price-feed join (`httpfs`), and time-travel notes
pointing at `06_ducklake.sql`.

**`public/` — client-side catalog search (DuckDB-WASM).** Ships the catalog as
Parquet and runs DuckDB *in the browser*: every keystroke, facet, and sort is a
real SQL query with zero round-trips, blending BM25 (`fts`) with an `ILIKE`
fallback so mid-word typing never flickers to zero results. "Ducks like this"
is a real text embedding (`vss`) whose neighbours are found once, in the browser,
with DuckDB 2.0's `NEAREST` join — the same engine version as the server, via
Query Farm's Haybarn build of DuckDB-Wasm. The console strip
at the bottom shows the generated SQL and its sub-millisecond execution time.
Reads and personalization live in the browser; **truth stays on the server**
(anything on the write path — checkout, inventory — is the OLTP tier). One
exception: "since you brought them home" fuses the same text embedding with a
DuckPGQ co-purchase graph traversal, and DuckPGQ doesn't load in DuckDB-WASM —
so that recommendation is a round-trip to `collector.py`
(`get_hybrid_recommendations()`), using the same tiered real-signal-first/
fallback pattern as `get_recommendations()`'s "shoppers like you also got."

## Notes on the synthetic data

Deterministic (`setseed`) so every run is identical. ~500 users, 60 products,
400 seeded historical orders + 1 live transaction, ~6,500 clickstream events
across 31 daily partitions. The funnel is engineered to ~33% view→cart and
~33% cart→purchase; retention has gentle built-in churn so the cohort triangle
decays instead of sitting flat.

## Known limitations

- **`oltp.duckdb` allows only one writer.** DuckDB's single-writer model
  means every order and every stock decrement funnels through
  `collector.py`'s one connection. Quack (port 8790) gives remote clients
  access, but they're still served by that one process.
- **`ducklake_snapshots()` doesn't work over quack.** `AT (VERSION => n)`
  does; the snapshot-listing function needs the file directly
  (`06_ducklake.sql`).
- Backing the DuckLake catalog with Postgres instead of a local file would
  give real concurrent multi-process reads/writes without funneling through
  one process.
